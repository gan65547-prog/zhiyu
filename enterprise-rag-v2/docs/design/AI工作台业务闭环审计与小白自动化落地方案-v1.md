# AI 工作台业务闭环审计与小白自动化落地方案 v1

> 审计日期：2026-08-11  
> 审计对象：`feature/ai-workbench-v0.2`，当前检查点 `8f1faf86`  
> 产品基线：`知域科技双产品定位与知域引擎执行决策-v1.md`、`AI工作台产品详细落地方案-v1.md`、`AI工作台与EdgeAI双产品协同落地方案-v1.md`  
> 审计结论：技术候选版可运行，但新用户业务闭环尚未完成，不应标记为稳定版。

## 1. 执行摘要

三份产品文档把第一阶段验收终点定义为：新用户不依赖开发人员解释，完成一次可追溯的 `素材 → 证据 → 洞察 → 行动`。当前版本已经具备素材、文档索引、知识卡片、证据、研究、Agent、内容、问答等多数底层对象和独立操作，但它们仍以多个页面、两套资料入口和多次人工触发存在。

因此，当前状态应准确表述为：

- DeepSeek、数据库、Redis、Qdrant、API 和 Worker 当前健康，真实模型链路可用。
- 文件、URL、文本可以进入素材系统；绑定知识库后可以进入文档解析和 RAG。
- 知识卡片有证据门禁、审核和版本；研究有来源、证据、发现、报告和审核。
- 这些能力没有被编排成一条面向小白的默认流程，用户需要理解素材、知识库、Dataset、知识卡片、Agent、研究运行等内部概念。
- 当前 E2E 主要证明页面可达和独立动作可运行，没有证明全新用户从首次导入到创建带来源行动的完整旅程。

发布判断：保留 `v0.2` 候选版身份，先完成本方案 P0，再进行稳定版 Go/No-Go。

## 2. 对上一轮结论的复核与修正

| 议题 | 复核结论 | 证据与补充 |
| --- | --- | --- |
| 智能问答是否接入 DeepSeek | 已真实接入 | 当前 `/health` 返回 `provider=deepseek`、`model=deepseek-v4-flash`，问答页已有真实语义回答。问题主要不在模型连通性，而在检索上下文与素材入口脱节。 |
| 为什么用户感觉问答不可用 | 主要是上下文断点 | 问答只接受 `dataset_id`，只检索已完成索引的 Dataset 文档。素材若未绑定目标知识库，会成为 `ready` 素材，却不会创建兼容 Document，也不能被问答检索。界面把目标知识库标为“可选”，没有说明这一后果。 |
| 是否只能一个文件一个文件上传 | 当前普通文件入口是单文件 | `AssetCenterView` 使用 `limit=1`，后端上传端点一次只接收一个 `UploadFile`，单文件上限 20MB。另有单 URL、单段文本和微信聊天导入，但没有面向普通用户的多文件、多 URL、文件夹或 ZIP 批量导入。 |
| 知识包导入能否替代批量文件 | 不能 | `/assets/import-knowledge-package` 当前登记外部知识包的授权、版本和门禁元数据，没有接收并展开普通文件集合，也没有自动完成内容解析。它是治理接口，不是小白批量导入入口。 |
| 知识星图是否全靠手工 | 不完全是 | 系统已有基于共享术语的规则候选，以及 DeepSeek 模型候选；候选不会自动成为正式关系，用户目前需逐条确认。模型建议还需要至少两张已审核卡片，并由用户主动点击触发。 |
| 自动化是否偏低 | 是 | 解析、提炼、关系建议、研究生成等单点自动化已经存在，但大多需要用户跨页逐次触发，缺少默认知识库、批次、统一编排、下一步深链接和可恢复的端到端进度。 |

## 3. 文档目标与当前实现差距

### 3.1 最小可信闭环评级

| 对象 | 当前能力 | 评级 | 主要缺口 |
| --- | --- | ---: | --- |
| Asset 素材 | 文件、URL、文本、原始存储、状态、重试、来源字段 | 部分完成 | 单文件；Dataset 可空；素材和文档双入口；无批次和默认去向。 |
| Evidence 证据 | 文档分块、知识证据、研究证据、原文引用和来源定位 | 部分完成 | 证据展示分散；普通用户看不到统一证据台；自动提炼只读取前 5 个分块。 |
| Knowledge 知识 | 卡片、证据门禁、审核、版本、回滚、关系网络 | 基础完成 | 素材提炼需手动点击；批量审核缺失；关系建议逐条确认；知识和 Dataset 的产品概念重叠。 |
| Insight 洞察 | 研究项目、问题、样本、运行、证据、发现、报告、审核 | 部分完成 | 创建项目时来源选择有限；未形成“从当前素材发起研究”的连续动作；研究发现审核粒度弱。 |
| Action 行动 | 可从已审报告生成内容草稿；Agent 可执行白名单工具 | 部分完成 | 没有统一 Action 对象；任务、方案、实验等行动缺失；内容中心过早承担主动作。 |
| Outcome 结果 | 内容发布记录、人工指标、规则复盘 | 弱完成 | 只覆盖内容场景；结果不能统一反哺知识或研究；外部平台仍主要依赖人工快照。 |

综合评级：底层能力约达到“可演示组件集”，核心用户旅程仍是“未闭环”。

### 3.2 当前两套资料链路

```text
链路 A：知识库 → 文档上传 → Worker 解析/向量化 → 智能问答

链路 B：素材中心 → Asset → 可选绑定知识库
                         ├─ 已绑定 → 兼容 Document → 解析/问答 → 手动提炼知识
                         └─ 未绑定 → ready 素材 → 无法进入智能问答/知识提炼
```

这不是简单的文案问题，而是当前最大的产品架构问题。用户从“素材中心”开始时，系统允许创建一个无法继续进入问答和提炼的孤立素材；用户从“知识库”开始时，又看不到新版工作台承诺的统一流水线。

短期不建议立即删除旧 Dataset/Document 模型。正确做法是建立统一应用层入口，让每次可检索导入都自动获得 Dataset 归属，并逐步把旧页面降为高级管理页。

## 4. 关键问题清单与优先级

### P0：阻断业务闭环

| 编号 | 问题 | 用户影响 | 根因 | 完成标准 |
| --- | --- | --- | --- | --- |
| P0-01 | 首次使用没有默认知识库 | 用户导入后不能问 | Dataset 仍是 RAG 必填对象，产品却把绑定设为可选 | 新工作空间自动或按首次导入创建默认知识库；普通导入默认绑定。 |
| P0-02 | 素材与知识库双入口 | 用户不知道从哪里开始 | 新 Asset 模型通过兼容字段接旧 Document，但 UI 同时暴露两套主入口 | 主入口统一为“资料”；知识库降为资料集合/高级管理。 |
| P0-03 | 没有批量导入 | 多资料场景操作成本过高 | 前端单文件限制，后端没有批次模型和批量端点 | 支持多文件拖放、多个 URL、批次状态、部分失败和单项重试。 |
| P0-04 | 导入后需手动提炼 | 用户无法获得自动知识草稿 | `organize` 是独立按钮和独立队列任务 | 默认流水线可自动执行到“知识草稿待审核”，用户只在治理点确认。 |
| P0-05 | 问答缺少就绪检查 | 空库、处理中和无命中看起来都像 AI 不工作 | 问答只展示“已连接知识库”，未展示文档数、索引状态和最近失败 | 发送前显示可检索文档数；不就绪时给出明确原因和一键修复。 |
| P0-06 | 任务中心只跳模块 | 用户到了页面仍要找具体对象 | 聚合任务只携带模块级 route | 每条任务带资源级深链接、错误原因、建议动作和原地重试/审核。 |
| P0-07 | 验收口径偏技术 | “路由通过”被误认为“业务完成” | E2E 分散验证页面与独立动作 | 增加首次用户单旅程 E2E，并作为稳定版硬门禁。 |

### P1：降低重复人工操作

| 编号 | 问题 | 改进 |
| --- | --- | --- |
| P1-01 | 星图候选要手动触发且逐条确认 | 卡片审核后自动异步生成候选；支持批量选择、证据预览和高置信度筛选。 |
| P1-02 | 研究来源选择与素材页割裂 | 在素材、知识卡片和问答回答上直接提供“加入研究”；研究创建器支持批量选择现有素材。 |
| P1-03 | 报告到行动类型单一 | 增加轻量 Action：任务、内容草稿、方案、实验；全部保留 `source_insight/report_id`。 |
| P1-04 | 结果只服务内容复盘 | 建立通用 Outcome 记录，支持手工结果、指标、反馈和结论修订。 |
| P1-05 | 导航仍暴露过多产品概念 | 收口为工作台、资料、知识、研究、行动、工作空间六项；问答作为全局助手和知识内入口。 |

## 5. 面向小白的目标体验

### 5.1 首次使用只回答三个问题

1. 你要处理什么资料？——拖入文件、粘贴网址或文本。
2. 你想用它做什么？——问资料、形成研究、整理知识。
3. 哪些结果需要你确认？——知识、关系、洞察和对外动作。

系统不应在首次旅程中要求用户理解 Dataset、向量化、分块、Agent Definition、Research Run 等实现概念。

### 5.2 目标主流程

```text
进入工作台
  → 拖入多个文件/URL/文本
  → 系统自动创建或选择默认资料库
  → 自动解析、去重、索引、摘要、标签和知识草稿
  → 页面显示“已可提问”
  → 用户直接提问或发起研究
  → 系统生成带证据的回答/报告
  → 用户确认知识、洞察或关系
  → 一键创建任务、草稿、方案或实验
```

### 5.3 工作台首屏

首屏只保留：

- 一个主要按钮：“导入资料”。
- 一个全局输入框：“问你的资料”。
- 一条当前流水线：“3 份处理中、2 份可提问、4 条待确认”。
- 三类下一步：“继续提问”“审核知识”“创建研究/行动”。
- 异常任务必须显示具体对象、原因和处理按钮。

不在首屏展示 Agent 定义、运行档案、数据连接器等高级概念。

### 5.4 自动化与人工门禁

| 自动完成 | 必须人工确认 |
| --- | --- |
| 建默认知识库、上传、解析、OCR/文本提取、分块、向量化、去重 | 将 AI 草稿批准为正式知识 |
| 摘要、标签、候选实体、知识草稿 | 将候选关系写入正式知识图谱 |
| 关系候选、研究计划、证据集合、报告草稿 | 批准洞察、报告和对外内容 |
| 失败重试建议、任务进度、来源完整性检查 | 外部发布、外部写操作、高风险 Agent 工具 |

原则：自动化负责准备、组织和建议；人工只停留在治理和外部影响节点。

## 6. 可落地产品与技术方案

### 6.1 统一导入批次

新增 `ingestion_batches`：

```text
id, tenant_id, workspace_id, dataset_id, created_by
status, total_count, completed_count, failed_count
options_json, created_at, updated_at, completed_at
```

`assets` 增加可空 `batch_id`。批次状态不替代单素材状态；单项可失败、重试和删除，批次负责聚合观察。

新增接口：

```text
POST /api/v1/onboarding/bootstrap
POST /api/v1/assets/import-batch              multipart，多文件
POST /api/v1/assets/import-urls               多 URL
GET  /api/v1/assets/batches/{batch_id}
POST /api/v1/assets/batches/{batch_id}/retry-failed
POST /api/v1/assets/{asset_id}/continue-to-knowledge
```

约束：

- 单文件继续保持 20MB 安全限制；批次总量设置部署级上限。
- 同一批次允许部分成功；失败项不回滚成功项。
- 按 `workspace_id + content_hash` 提示重复，允许跳过或保留新版本。
- URL 继续复用 SafeFetcher 的 SSRF、MIME、重定向和大小门禁。

### 6.2 默认资料库与兼容策略

新增 `ensure_default_dataset(workspace_id, user_id)` 应用服务：

- 新工作空间首次导入时创建“我的资料库”。
- 素材导入未显式选择 Dataset 时绑定默认资料库。
- 高级用户仍可在导入前选择其他资料库。
- 历史 `dataset_id IS NULL` 且有可解析原文的素材提供“一键加入资料库”迁移动作，不静默移动用户数据。

短期保留 Dataset/Document 作为 RAG 运行模型，对用户统一称为“资料库/资料”。待所有新入口稳定后，再评估数据库层合并。

### 6.3 一条可恢复的处理编排

复用 AgentRun/AgentRunStep 记录以下默认工作流：

```text
store_source
→ create_document
→ parse_and_index
→ summarize_and_tag
→ propose_knowledge
→ propose_relations
→ ready_for_chat
→ human_review
```

每一步要求：幂等、可重试、记录输入输出摘要、错误原因和耗时。用户在批次页看到业务语言，不看到队列名称。

“自动提炼知识”作为导入选项默认开启；关闭后流程停在 `ready_for_chat`。现有 `/organize` 保留为兼容入口，内部转调统一编排服务。

当前知识提炼只读取前 5 个文档分块，应改为：先基于全文分块做覆盖采样/聚类，再选择代表性证据；报告中记录总分块数、使用分块数和遗漏风险。

### 6.4 问答就绪检查

新增接口：

```text
GET /api/v1/chat/readiness?dataset_id=...
```

返回：

```json
{
  "ready": true,
  "indexed_documents": 3,
  "processing_documents": 1,
  "failed_documents": 0,
  "last_indexed_at": "...",
  "provider_status": "healthy",
  "reasons": [],
  "actions": []
}
```

前端规则：

- 无资料：显示“先导入资料”，提供同页导入。
- 正在处理：允许等待并显示进度，不发送必然无结果的请求。
- 有失败：显示失败资料和重试入口。
- 可提问：显示“基于 3 份已索引资料回答”。
- 无相关证据：回答必须区分“系统正常但资料中没有答案”和“模型/检索失败”。

### 6.5 知识星图自动建议

保留“候选不自动成为事实”的治理边界，改进触发和确认效率：

- 知识卡片审核通过后投递关系候选任务。
- 先运行低成本规则候选，再按配置运行 DeepSeek 候选。
- 候选保存到独立 `knowledge_relation_suggestions`，记录来源、模型、版本、分数、解释和证据 ID，不只临时返回。
- 前端支持按置信度筛选、批量勾选、批量接受/忽略。
- 默认不提供“无审核全自动入图”；如未来开放，只允许白名单关系类型和极高置信度，并保留撤销与审计。

新增接口：

```text
POST /api/v1/knowledge/relations/suggestions/generate
GET  /api/v1/knowledge/relations/suggestions
POST /api/v1/knowledge/relations/suggestions/batch-review
```

### 6.6 洞察到行动

增加轻量 `actions` 表，避免把所有行动都等同于内容草稿：

```text
id, tenant_id, workspace_id, action_type
title, description, status, assignee_id, due_at
source_research_report_id, source_finding_id, source_knowledge_item_id
created_by, created_at, updated_at, completed_at
```

首期 `action_type` 只支持 `task`、`content_draft`、`proposal`、`experiment`。报告审核通过后至少提供一个“创建下一步行动”入口；内容草稿继续复用现有 ContentDraft，并通过 Action 关联来源。

### 6.7 任务中心与深链接

任务聚合返回：

```text
resource_type, resource_id, route, action_key
reason, suggested_action, can_retry, can_review
```

页面支持安全的原地动作：重试素材、审核知识、审核关系候选。复杂编辑仍跳到资源详情，并定位具体对象，不能只跳到模块首页。

### 6.8 导航收口

普通用户主导航调整为：

```text
工作台 ｜ 资料 ｜ 知识 ｜ 研究 ｜ 行动 ｜ 工作空间
```

- 首页与 AI 工作台合并。
- 素材层与知识库统一到“资料”，Dataset 管理作为二级页。
- 知识卡片与知识星图归入“知识”。
- Agent、任务中心、运行档案归入“行动”的二级页。
- 内容和数据中心仅从行动/复盘进入。
- 智能问答保留全局助手，不再作为孤立主流程。

## 7. 分阶段实施计划

### 阶段 0：口径与基线冻结（0.5～1 天）

- 将当前版本标记为候选，不创建稳定 tag。
- 固化一个干净新用户、一个工作空间和一组小型验收资料。
- 记录当前首个可提问时间、操作次数和失败原因。
- 更新 Release Profile，使测试数量、测试时间和当前 commit 一致。

### 阶段 1：P0 业务闭环（6～9 个开发日）

| 顺序 | 任务 | 预计 |
| ---: | --- | ---: |
| 1 | 默认资料库服务、历史空绑定检查、一键加入资料库 | 1 天 |
| 2 | 批次模型、多文件/多 URL API、单项重试 | 2 天 |
| 3 | 拖放导入向导、批次进度与部分失败 UI | 1.5 天 |
| 4 | 导入到知识草稿的统一编排与幂等恢复 | 1.5 天 |
| 5 | 问答 readiness、空态、失败态和一键修复 | 1 天 |
| 6 | 任务深链接与关键原地动作 | 0.5 天 |
| 7 | 首次用户全旅程 E2E、回归和发布证据 | 1～1.5 天 |

阶段 1 完成后，新用户应能在一个页面开始，在不理解 Dataset 的情况下完成导入、等待、提问和知识审核。

### 阶段 2：P1 自动化与行动（4～6 个开发日）

- 关系候选持久化、自动触发、批量审核。
- 素材/知识到研究的直接入口和多素材选择器。
- 统一 Action 最小模型和“报告 → 行动”入口。
- 首页改成基于状态的下一步，不再展示平行模块清单。
- 收口普通用户导航。

### 阶段 3：P2 复盘增强（真实用户验证后）

- 通用 Outcome 和行动结果回写。
- 基于真实需求选择一个官方连接器。
- 多模态、文件夹同步和更大批次导入。
- 不在 P0/P1 闭环稳定前扩展平台数量或开放自主 Agent。

## 8. 验收与测试方案

### 8.1 稳定版唯一主旅程

使用全新账号和空工作空间，浏览器真实执行：

```text
登录
→ 拖入 3 个文件，其中 1 个重复、1 个合法、1 个故意失败
→ 系统自动建立默认资料库
→ 成功项完成解析和索引，失败项显示原因并可重试
→ 自动生成带证据知识草稿
→ 在同页进入问答并获得带引用回答
→ 审核一张知识卡片
→ 自动出现关系候选并批量确认
→ 从资料发起研究
→ 查看带证据和限制的报告并审核
→ 创建一个可追溯行动
```

该旅程任一步需要开发者修改数据库、手动投递队列、解释内部概念或绕过界面，均判定未通过。

### 8.2 必测异常

- DeepSeek 401、超时、限流和空响应。
- Worker 未运行、任务超时和任务重启恢复。
- 空知识库、处理中、索引失败、检索无命中。
- 批次部分失败、重复文件、超大文件、不支持 MIME。
- URL SSRF、重定向、超限和不可访问。
- 跨租户、跨工作空间和失效权限。
- 关系候选生成失败不能影响知识审核。
- 行动创建必须保留来源；无来源的正式洞察不得通过。

### 8.3 发布硬门禁

- 当前 commit 对应的前端 type-check/build、后端测试、迁移检查全部通过。
- API、Worker、数据库、Redis、Qdrant、Embedding、DeepSeek 健康。
- 首次用户主旅程通过，不只做路由矩阵。
- Release Profile 记录命令、时间、环境、测试数、失败数和产物位置。
- 回滚镜像/commit 已验证；候选 tag 与测试 commit 完全一致。

## 9. 指标与目标

| 指标 | P0 目标 |
| --- | ---: |
| 从登录到开始导入的点击数 | ≤ 2 |
| 导入后到首次可提问的人工操作数 | 0 |
| 3 文件批量导入需要的提交次数 | 1 |
| 首个带引用回答成功率 | ≥ 90%（合法样本） |
| 正式知识证据覆盖率 | 100% |
| 不可解释失败率 | 0 |
| 关系候选批量处理能力 | ≥ 20 条/次 |
| 洞察到行动转化 | 每个已审报告至少可创建 1 个行动 |

产品北极星继续采用“首个可信洞察时间”，不能用页面数、接口数或模型调用次数替代。

## 10. 风险与控制

| 风险 | 控制 |
| --- | --- |
| 自动化生成大量低质量知识 | 只自动生成草稿；证据门禁和人工审核保持不变。 |
| 自动关系污染星图 | 候选持久化但不自动正式入图；批量确认可撤销、可审计。 |
| 批量导入拖垮 Worker | 批次总量限制、队列限速、单项任务、背压和可取消。 |
| 默认知识库造成历史数据混淆 | 只影响新导入；历史空绑定素材由用户一键迁移。 |
| 继续维护两套模型增加复杂度 | 先用应用层门面统一体验；待真实迁移数据验证后再合并表。 |
| DeepSeek 健康但回答仍差 | readiness 只证明依赖可用；回答必须显示检索来源、无命中和证据覆盖。 |
| 测试再次高估闭环 | 稳定版以首次用户单旅程为硬门禁，路由矩阵只能作为辅助证据。 |

## 11. 明确不纳入本轮

- 不操作或改造 Vislbox 仓库。
- 不接入大量社交平台或未授权抓取。
- 不开放无人审核的外部发布和自主 Agent。
- 不引入独立图数据库。
- 不把视觉重做当作业务闭环交付。
- 不在 P0 阻断项未完成时扩展更多一级页面。

## 12. Definition of Done

本方案完成的标志必须同时满足：

1. 新用户只从“导入资料”开始，即可批量导入并自动获得可检索上下文。
2. 所有成功资料自动完成解析、索引，并可选择自动生成待审核知识草稿。
3. 智能问答明确显示使用范围、索引状态、引用和失败原因。
4. 知识星图自动产生候选，用户可以带证据批量确认，不必逐条手建。
5. 已审核研究报告可以创建至少一种带来源的行动。
6. 首次用户端到端旅程在真实 DeepSeek、Worker 和向量库环境中通过。
7. 发布证据与当前 commit 一致，工作区无未解释改动，且具备可验证回滚点。

在上述七项全部满足前，产品可以称为“可运行候选版”，不能称为“业务流程和功能全部完成”。
