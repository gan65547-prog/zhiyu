### 0.1 统一后的模块边界

| 层级 | 统一名称 | 责任 |
|---|---|---|
| 产品总层 | AI 工作台 | 统一入口、导航、待办、任务和权限 |
| P0 能力 | 素材中心 | 接收文件、用户指定 URL、聊天和后续连接器素材 |
| P0 能力 | 知识中心 | Dataset、知识卡片、Wiki、证据引用和审核 |
| P0 能力 | 研究闭环最小版 | 研究问题、证据、限制说明、审核判断和一个行动 |
| P1 能力 | 完整研究洞察 | 内部 RAG、外部检索、多来源证据、研究报告 |
| P1 实现机制 | Agent 工作流 | 以显式步骤编排素材整理、研究分析和知识沉淀；不做开放式自主 Agent |
| P2 能力 | 内容中心 | 选题、草稿、发布记录和效果复盘 |

研究模块不单独建设一套“上传系统”；所有用户上传文件和用户指定 URL 先进入素材中心。研究模块只负责把素材中心、内部知识库和受控外部来源组合成研究项目和研究运行。

### 0.2 统一术语

- `research_project`：用户可见的研究项目，保存主题、问题、范围和目标。
- `research_run`：研究项目的一次执行，可重试、取消和保留版本。
- `research_source`：项目或运行引用的来源。
- `research_evidence`：来源中的证据片段。
- `research_finding`：由证据支持的事实、观点或结论。
- `research_report`：一次运行生成的报告。

后续实现不得再引入独立的 `research_task` 作为第二套核心模型；如果代码中需要任务对象，统一使用 `research_run`。

## 1. 项目背景

当前系统已经具备企业级 RAG 的基础能力，包括：

- 多租户和工作空间管理
- 用户、成员和权限控制
- 知识库创建和管理
- 文档上传及处理
- 微信聊天记录导入
- 基于知识库的流式问答
- 会话历史和来源引用
- 学习诊断能力
- 订阅和用量控制

现有产品更接近“可检索的知识库系统”。参考的 AI 工作台类产品则进一步完成了以下闭环：

```text
采集外部信息
    ↓
整理和理解素材
    ↓
形成知识、观点和研究洞察
    ↓
由 Agent 执行自动化任务
    ↓
生成内容或业务动作
    ↓
收集结果数据并复盘
    ↓
反哺知识库和 Agent
```

本方案的重点不是简单增加页面，而是补齐“洞察、执行和反馈”三层能力。

## 2. 产品定位

### 2.1 产品定义

AI 工作台是面向个人和小团队的信息处理与智能执行平台，帮助用户把分散的文件、网页、聊天和用户授权的业务资料，持续转化为：

- 可检索的素材
- 可维护的知识
- 可追溯的证据
- 可验证的洞察
- 可执行的任务
- 可发布的内容
- 可复盘的业务结果

### 2.2 核心价值

| 价值 | 说明 |
|---|---|
| 信息集中 | 将不同来源的数据统一进入素材中心 |
| 知识沉淀 | 将原始资料加工为可维护的 Wiki 和知识卡片 |
| 研究提效 | 从样本中自动提炼需求、观点、证据和结论 |
| 自动执行 | 通过可追踪的 Agent 工作流完成重复任务 |
| 内容转化 | 将洞察转化为选题、草稿和多平台内容 |
| 结果反馈 | 用发布和业务数据反哺知识与决策 |

### 2.3 产品边界

本项目第一阶段不追求建设开放式自主 Agent 平台，也不直接复制某个外部产品。第一阶段优先建设：

1. 可靠的数据采集和证据链
2. 可理解的知识组织
3. 可追踪的研究和 Agent 工作流
4. 从资料到结论的最小闭环

## 5. 核心业务闭环

### 5.1 用户主流程

```text
用户上传文件或粘贴网页
        ↓
系统创建素材并保存原始内容
        ↓
异步解析、清洗、切分、去重
        ↓
提取摘要、主题、实体、观点和证据
        ↓
生成待确认知识卡片
        ↓
用户确认或修改
        ↓
写入 Wiki、向量库和关系网络
        ↓
问答、研究和 Agent 任务可复用
```

### 5.2 研究流程

```text
创建研究项目
→ 定义研究问题
→ 选择素材和数据源
→ 样本清洗与聚类
→ 提取需求和观点
→ 绑定原文证据
→ 生成判断和结论
→ 人工确认
→ 输出报告
```

### 5.3 内容流程

```text
研究洞察
→ 生成选题
→ 生成内容草稿
→ 多平台改写
→ 人工审核
→ 发布记录
→ 导入效果数据
→ 自动复盘
```

## 6. 工作台总览设计

当前首页应从“系统欢迎页”升级为“下一步行动中心”。

### 6.1 顶部状态区

展示以下指标：

- 素材总数
- 知识条目数
- 最近 7 天新增素材
- 待确认知识条目数
- 运行中的 Agent 任务数
- 失败任务数
- 研究项目数
- 内容草稿数
- 知识库健康度
- 最近一次同步时间

### 6.2 今日行动区

系统根据状态生成行动项：

- 失败的素材处理任务
- 待确认的知识卡片
- 待补充证据的研究结论
- 待审核的内容草稿
- 长时间未更新的知识条目
- 待运行的定时 Agent

### 6.3 最近活动区

展示：

- 最近导入的素材
- 最近生成的知识卡片
- 最近完成的研究
- 最近的问答和引用
- 最近生成的 Agent 产物
- 最近发布的内容

### 6.4 推荐洞察区

系统可以根据已有素材推荐：

- 反复出现的用户需求
- 突然增长的主题
- 资料之间的冲突观点
- 尚未形成知识条目的高频内容
- 适合转化为研究或内容的主题

## 7. 素材中心方案

### 7.1 支持的素材类型

P0 首期支持：

- PDF、Word、Excel、Markdown、TXT
- 微信聊天记录
- 网页 URL
- 手动粘贴文本

P1 及以后扩展：

- 图片 OCR 和截图理解
- 音频和视频转写文本
- 浏览器插件
- 网盘同步
- RSS 和订阅源
- 企业微信、飞书、Notion、GitHub
- 社交平台公开数据

### 7.2 素材状态机

```text
待处理
  ↓
解析中
  ↓
已解析
  ↓
分析中
  ↓
待人工确认
  ↓
已入库
```

异常分支：

```text
解析失败 / 分析失败
        ↓
记录错误原因
        ↓
可重试 / 可人工处理 / 可忽略
```

### 7.3 素材字段

每条素材至少保存：

- `id`
- `tenant_id`
- `workspace_id`
- `title`
- `asset_type`
- `source_type`
- `source_url`
- `source_author`
- `published_at`
- `imported_at`
- `raw_storage_path`
- `parsed_text`
- `summary`
- `processing_status`
- `processing_error`
- `content_hash`
- `metadata`
- `created_by`
- `created_at`
- `updated_at`

### 7.4 原始内容和派生内容分离

必须保留以下层级：

```text
原始文件 / 原始网页
      ↓
解析后的完整文本
      ↓
文本分块
      ↓
结构化实体、主题、观点
      ↓
摘要、知识卡片和向量
```

任何摘要和 AI 结论都不能替代原始证据。

## 9. 证据链方案

### 9.1 证据链原则

所有 AI 生成的关键结论，都应能回溯到原始素材。证据链最少包含：

- 原文内容
- 原文位置
- 来源素材
- 来源平台
- 时间
- 摘录内容
- 支持的观点或结论
- 置信度
- 是否经过人工确认

### 9.2 证据卡片

示例：

```text
结论：用户更愿意使用自动整理后的结果，而不是单纯的资料存储。

支持证据：12 条
反对证据：3 条
样本数量：86
来源平台：网页、小红书、抖音
置信度：中高
适用范围：个人知识管理用户
最后更新时间：2026-08-05
```

### 9.3 前端交互

证据卡片应支持：

- 查看原文
- 跳转原文位置
- 高亮引用
- 加入研究项目
- 生成知识卡片
- 标记为支持证据
- 标记为反例
- 修改或删除 AI 提取结果

## 11. Agent 中心方案

### 11.1 首批 Agent

| Agent | 输入 | 输出 |
|---|---|---|
| 素材整理 Agent | 文件、网页、聊天 | 分类、标签、摘要 |
| 研究分析 Agent | 研究主题和样本 | 需求、观点、证据、结论 |
| 知识沉淀 Agent | 已解析素材 | Wiki、知识卡片、关系 |
| 内容创作 Agent | 知识和研究结论 | 选题、标题、正文 |
| 数据复盘 Agent | 发布和反馈数据 | 表现分析、改进建议 |
| 项目助手 Agent | 项目资料和任务 | 项目问答、计划、风险 |

### 11.2 Agent 任务模型

每次运行记录：

- Agent 类型
- 任务名称
- 输入素材
- 使用的知识库
- 执行步骤
- 当前状态
- 中间结果
- 最终产物
- 使用模型
- Token 消耗
- 错误信息
- 重试次数
- 人工确认节点
- 操作日志

### 11.3 任务状态

```text
草稿 → 排队中 → 执行中 → 等待确认 → 已完成
                         └→ 失败 → 可重试
```

### 11.4 第一版采用工作流而非完全自主 Agent

推荐将任务拆为显式步骤：

```text
读取素材
→ 去重
→ 提取主题
→ 生成摘要
→ 提取证据
→ 生成结论
→ 人工确认
→ 写入知识库
```

这样可以保证可解释、可恢复、可测试和可审计。

## 12. 内容中心方案

内容中心属于 P2，不应阻塞第一期，但数据模型需要提前设计。当前已落地选题、草稿创建/编辑、审核、人工/外部系统发布记录、未来排期、到期排期 Worker 状态推进、发布日历查询、指标回写、可查询且幂等的规则化复盘基础闭环（`033_add_content_center`、`034_add_content_publish_metrics`、`035_add_content_retrospectives`）。审核通过的研究报告还可通过受控接口生成带报告、运行、证据和发现 ID 的待审核内容草稿，形成“研究—内容”最小闭环；发布执行已抽出白名单连接器端口和注册表，当前仅注册 `manual` 连接器并进入待手动确认状态。已增加确定性的微信、X、知乎、网站四类平台改写 API/UI，结果写入草稿 `metadata.platform_variants`，不改变原稿和审核状态；新增模型改写模式，结果单独写入 `metadata.platform_model_variants`，记录源内容哈希、Provider/模型并强制标记人工审核。新增工作空间级内容连接器凭据管理：凭据使用 `ENCRYPTION_KEY` 以 Fernet 密文保存，API 只返回掩码元数据，发布/排期可绑定凭据并在 Worker 执行前复核租户和工作空间归属（`040_add_content_connector_credentials`）；真实平台自动发布 SDK 尚未接入，未注册连接器不会因存在凭据而执行外部请求。

### 12.1 内容流程

## 20. 安全和治理要求

### 20.1 数据隔离

### 20.3 AI 结果治理

- 关键结论必须显示来源
- 低置信度结论必须标记
- 研究报告支持人工审核
- 知识条目支持版本和回滚
- Agent 关键操作需要审批

## 25. 结论

现有项目不需要推倒重来。最合理的路径是保留当前企业级 RAG、租户、权限和问答基础，在上层增加：

```text

→ 研究洞察
```

第一期应围绕以下目标交付：

> 用户能够把一份文件或一个网页放进系统，系统自动整理出知识和证据，用户确认后发起研究，并最终得到一份可追溯、可执行的结论报告。

### 26.2 研究数据模型

研究模块只使用以下核心对象：

```text
research_projects       用户可见研究项目
research_questions      项目中的问题和子问题
research_samples        项目选中的 Asset、Dataset 或 URL
research_runs           项目的一次执行和版本
research_sources        本次运行检索/抓取到的来源
research_evidence       来源中的证据片段
research_findings       有证据支撑的事实、观点、结论
research_reports        本次运行的结构化和 Markdown 报告
```

所有对象均包含：

```text
tenant_id
workspace_id
created_by
created_at
updated_at
deleted_at
```

关键关系：

```text
research_project 1 ── N research_questions
research_project 1 ── N research_samples
research_project 1 ── N research_runs
research_run     1 ── N research_sources
research_source  1 ── N research_evidence
research_run     1 ── N research_findings
research_run     1 ── 1 research_report
research_run     1 ── 1 agent_run
```

`research_run` 至少包含：

- `project_id`、`tenant_id`、`workspace_id`；
- `status`：`pending/planning/searching/fetching/analyzing/generating/reviewing/completed/failed/cancelled`；
- `plan`：子问题、来源范围和模型配置；
- `limits`：来源数、网页大小、token、总耗时；
- `progress`、`current_stage`、`error_message`；
- `started_at`、`completed_at`、`retry_count`。

`research_findings` 至少包含：

- `claim`、`claim_type`、`confidence`；
- `evidence_ids` 或关联表；
- `conflict_status`、`needs_review`；
- `review_status`、`reviewer_id`、`reviewed_at`。

`research_reports` 至少包含：

- `run_id`、`version`、`content_markdown`、`content_json`；
- `model_name`、`prompt_version`；
- `citation_completeness`、`review_status`；
- `published_dataset_id`、`published_document_id`。

### 26.3 Agent 运行关系

Agent 不是另一套业务任务，而是 `research_run` 的执行器：

```text
research_run
  └── agent_run
       ├── plan
       ├── search_internal
       ├── search_external
       ├── fetch_sources
       ├── extract_evidence
       ├── synthesize_findings
       ├── generate_report
       └── human_review
```

`research_run` 负责对外状态、权限、配额和报告；`agent_run` 负责步骤状态、重试、日志和中间产物。取消或重试必须由 `research_run` 统一发起。

### 26.5 安全 URL 获取器

文件、用户 URL、外部搜索结果必须共用一个 `SafeFetcher`，不允许各模块自行实现抓取逻辑。

强制规则：

- 仅允许 `http/https`；
- 拒绝 localhost、环回、私有网段、链路本地和云元数据地址；
- DNS 解析后和每次重定向后重新校验 IP；
- 限制重定向次数、响应大小、连接时间和总时间；
- 校验 MIME、文件扩展名和压缩包展开大小；
- 记录 robots/站点条款处理结果、来源许可和抓取时间；
- 外部内容作为不可信数据传给模型，不能改变工具权限或系统指令；
- P0 URL 导入与 P1 外部调研共用同一安全策略。

### 26.6 数据保留和删除

- 未发布的研究项目可由创建者删除，来源正文进入异步清理；
- 已发布知识删除时，正式知识停止检索，但保留最小审计关系；
- 受审核、合规或法务保留的数据使用 `legal_hold`；
- 来源表保留 URL、哈希、发布时间和抓取记录，正文按租户保留策略清理；
- `deleted_at` 表示业务不可见，`purged_at` 表示物理清理完成。

只要这条闭环稳定，产品就会从“企业知识库”进入“AI 工作台”阶段；后续的内容中心、平台数据和生态连接器，都可以在这个闭环之上逐步扩展。

运行时验收补充（2026-08-06）：已在本地 PostgreSQL/Redis/Qdrant 运行环境完成迁移和设置接口真实回归。`user_configs` 的主题/语言使用非原生 enum 映射，避免迁移表为 `VARCHAR` 而 ORM 绑定 PostgreSQL enum 类型不一致；凭据库兼容历史高熵字符串密钥并派生标准 Fernet key。配置 GET/PUT、API Key 新增/脱敏列表/删除均已通过。生产启动仍必须显式提供强 `JWT_SECRET`、有效 `INTERNAL_API_KEYS` JSON 列表、无尾随空格的布尔配置和持久化 `ENCRYPTION_KEY`。
