# 工程质量与发布治理

> **状态**：当前有效（2026-08-05）  
> **适用范围**：`enterprise-rag-v2`、`ops-center` 及 AI 工作台后续模块  
> **执行入口**：仓库根目录 `AGENTS.md`、`scripts/quality/`、`release/`

## 1. 目标和完成状态

本体系从 Vislbox 的工程治理模型迁移而来，但只保留适合 Python/RAG 服务的控制项。目标是让“完成”和“可上线”由当前候选的可复现证据决定，而不是代码存在、历史报告、服务存活或口头说明。

| 状态 | 含义 | 最低条件 |
|---|---|---|
| `planned` | 范围、非目标、风险、验收和回滚已定义 | 任务或 PR 有完整入口卡 |
| `implemented` | 代码已变更 | 尚未代表验证通过 |
| `verified` | 当前 HEAD 的必跑测试和质量门禁通过 | 命令、结果和候选提交可追溯 |
| `approved` | 独立审核确认 | 审核覆盖当前 HEAD，不使用旧提交结论 |
| `released` | 同一候选已部署且可回滚 | 发布证据、备份恢复和回滚记录完整 |

## 2. 变更分级

执行 `bash scripts/quality/classify-change-profile.sh` 自动给出最低档位；档位只能因风险升级，不能人为降级。

| 档位 | 触发 | 最低要求 |
|---|---|---|
| Fast | 仅 `documents/` 或 Markdown 变更 | 文档链接、格式与索引检查 |
| Standard | 普通业务代码、前端或运行配置变更 | 全量质量门禁 + 受影响服务测试 |
| Critical | API/Service、迁移、配置安全、部署、ops-center、CI/门禁、发布文件；或改动超过 200 行/5 个代码文件 | Standard 全部要求 + 权限/失败路径/回滚说明 + 独立审核 |

对 AI 工作台的 URL 抓取、跨租户资源、Agent 异步运行、研究来源和外部连接器，默认按 Critical 管理。

## 3. 每次开发的固定动作

1. 写明目标、非目标、风险域、验收和回滚；新模块或高风险改动补充相关技术方案。
2. 小步实现。每完成一个独立能力就运行受影响测试，不把多个功能点累积到最后一起验证。
3. 运行统一门禁：

```bash
bash scripts/quality/run-quality-gates.sh --full
```

门禁默认优先使用 `enterprise-rag-v2/.venv/bin/python`，保证本地核心回归和项目依赖一致；ops-center 若存在独立 `.venv` 则使用其解释器，CI 或特殊环境可通过 `PYTHON_BIN`/`OPS_PYTHON_BIN` 显式指定。`--full` 默认跑可重复的核心回归集合，并显式加载项目需要的 `pytest-asyncio`、关闭无关全局 pytest 插件自动发现，避免本机插件扫描导致假性卡死；手工、真实集成、性能和服务启动探测必须在具备对应基础设施时单独执行，不能把会长时间等待的探测混入默认门禁。当前 `test_document_copy_service.py` 因仍同步依赖真实文档向量化服务，暂列集成测试，待改为队列处理后回归核心集合。不能用系统解释器缺少依赖的结果替代项目环境验证。

4. PR 中附上真实执行命令和结果；涉及权限、数据、迁移、部署或外部抓取时，必须包含拒绝路径/失败路径证据。
5. CI 通过后再合并。CI 的成功才是候选的共享证据，本地结果只用于开发反馈。

## 4. 当前自动门禁

| 门禁 | 目的 | 执行位置 |
|---|---|---|
| `git diff --check` | 防止格式与补丁错误 | 本地、CI |
| Release Profile 校验 | 防止版本没有必测能力、负责人、测试和排除项 | 本地、CI |
| 活跃文档链接检查 | 防止导航和活跃文档失效 | 本地、CI |
| 变更分级 | 防止高风险修改伪装为文档或普通改动 | 本地、CI |
| Python `compileall` | 发现基础语法错误 | 本地、CI |
| 双服务 pytest | 验证 `enterprise-rag-v2` 与 `ops-center` 行为 | CI |
| 代码结构门禁 | 阻止新增/增长的大文件、大函数和高圈复杂度函数 | 本地、CI |
| AI 工作台运行时验收 | 确认 API、数据库、Redis、Qdrant、Worker、Celery Beat 同时运行 | 具备 Docker 的集成环境 |
| 发布预检 | 绑定当前 HEAD、Profile、自动证据与人工演练证据 | 发布前 |

门禁脚本、CI 工作流或 Release Profile 的改动本身属于 Critical；修改后必须证明新规则在 CI 中被调用，并至少做一次反向验证（构造不合规输入应失败）。

## 5.1 代码结构与业务流程门禁

代码结构门禁执行（同时覆盖 Python 后端与 Vue/TypeScript 前端）：

```bash
python3 scripts/quality/check-code-structure.py \\
  --root enterprise-rag-v2/api \\
  --root enterprise-rag-v2/services \\
  --root enterprise-rag-v2/core \\
  --root enterprise-rag-v2/infrastructure \\
  --root ops-center/app \\
  --baseline scripts/quality/code-quality-baseline.json

python3 scripts/quality/check-frontend-structure.py \
  --root enterprise-rag-v2/frontend/src \
  --repo-root . \
  --baseline scripts/quality/frontend-quality-baseline.json
```

默认关注值为：文件 800 行、函数 120 行、圈复杂度 15，以及源代码单行 500 字符。它们用于识别结构风险，不要求为了过门禁机械拆分。既有超标项必须进入 baseline 并说明业务原因；baseline 项默认允许在 `max(30%, 50 行)`（文件）或 `max(20%, 30 行)`（函数）的预算内正常增长，也可以为明确的高内聚领域登记经评审的 `growth_budget_lines`/复杂度预算。超长源代码行不计入业务逻辑增长预算：历史超长行只保留数量和最大长度基线，新增超长行或继续压缩既有行直接阻断；将表达式换成可读的多行格式不等于拆分业务职责。范围内只给出 P2 review warning；即使历史债务跨过绝对硬阈值，只要仍在已批准的增长预算内，也只警告并要求 review。新增超标项或超出增长预算仍阻断；绝对硬顶主要用于新增结构债务和超预算增长。也就是说，新增功能可以按高内聚、低耦合的自然边界增长，不需要为了数字拆成低内聚的碎片；但不能把新的结构债务伪装成正常增长。baseline 必须说明业务原因，重构时应下降而不是刷新上限。

模块边界是硬规则：API 新增 ORM/数据库直连、Service/Core 反向依赖 API、任务跨层绕过端口，直接阻断。结构规模属于预算治理，正常业务增长可以通过审查继续，但必须留下 warning 和任务/PR 说明。门禁判断顺序固定为“先看既有债务基线，再看本次增量，再看业务边界”：同一高内聚用例在职责清晰、依赖方向正确、测试覆盖充分时，可以消耗正常增长预算；不能为了压行数把一个事务、一条状态机或一个稳定策略拆成低内聚碎片。只有新增违规、超出既有预算或触及硬顶才阻断；需要例外时必须补充业务原因、替代方案和后续偿还计划，不能直接刷新 baseline。

业务流程必须满足：

- API 只做协议适配、参数校验、鉴权和响应转换；数据库查询和业务编排进入 Service。
- Service 以一个用例为单位组织事务、权限、幂等、状态转换和失败策略；不得把抓取、解析、向量化、报告生成全部堆进一个方法。
- Core 只放可测试的领域规则和算法；Infrastructure 负责数据库、队列、存储、HTTP 客户端等外部适配。
- 异步任务只传递资源 ID 和版本/幂等信息；Worker 重新加载资源并校验租户，禁止把大正文塞进消息队列。
- 每条主流程都必须有成功、权限拒绝、重复提交、外部超时、解析失败和重试恢复测试。

### 5.2 运行时验收

定时 Agent 任务依赖 Celery Beat，不能只验证 API 和 Worker。具备 Docker daemon 的集成环境执行：

```bash
bash enterprise-rag-v2/scripts/verify-ai-workbench-runtime.sh \\
  enterprise-rag-v2/docker-compose.yml http://localhost:8000
```

脚本只读检查 Compose 是否声明并运行 `db`、`redis`、`qdrant`、`web`、`worker`、`beat`，随后检查 `/health/ready`。Docker daemon 不可用时返回 `BLOCKED`，不能伪报通过；本地单元测试通过也不能替代这项运行时证据。

## 5. 发布治理

发布使用 [release/release-profile.json](../../release/release-profile.json) 定义版本范围。每个 required capability 都要有可断言的验收、测试命令、风险等级、负责人和证据类型。

发布顺序：

```text
draft → rc → verified → approved → tagged → released
```

- `FAIL`、`BLOCKED`、`NOT RUN`、`UNKNOWN`、证据缺失或证据不属于当前 HEAD，均阻断 tag。
- 使用 `collect-release-evidence.py` 执行自动命令并写入候选 HEAD、退出码、耗时和输出哈希。
- 备份恢复、回滚、告警与真实环境权限验证等混合项目必须以 `--manual-evidence` 附上记录及文件哈希。
- `release-preflight.py` 通过后，部署脚本才允许创建 tag；脏工作区发布已被禁止。
- 旧 tag 不可移动、复用或用新证据覆盖。

详见 [发布 Runbook](../deployment/release-runbook.md)。

## 6. 明确不迁移的 Vislbox 专属门禁

RGA/DMA-BUF/MPP/V4L2、C/C++ 内存/锁/FD 生命周期、板端验收、systemd 进程杀伤安全和硬件性能预算均不适用于当前项目，因此不应复制后“空跑”。未来引入本地推理、摄像头或边缘设备时，再按实际风险建立对应契约和测试。

同样，GitHub 强制审批名单、受保护分支、制品/证据 Registry 需要在仓库与部署平台侧配置；本仓库已准备规则和证据格式，但不能由文档代替平台权限设置。
